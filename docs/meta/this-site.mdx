# How this site works

## Context

A documentation engineer's portfolio should itself be a documentation
project. Not a WordPress page with a "docs" theme — an actual, buildable,
reviewable docs repository with a working delivery pipeline.

## Toolchain

- **Docusaurus 3** (classic preset, TypeScript config). Chosen over Antora
  for a solo portfolio: one build, first-class GitHub Pages integration, and
  MDX for the interactive components.
- **Node 20**, `npm` for dependencies and scripts.
- **GitHub Pages** as the artifact host; the repo is a user-site
  (`<user>.github.io`) so it serves from the domain root.
- **GitHub Actions** builds and deploys. No manually committed `build/`
  output — the Pages artifact comes straight from CI.

## Repo structure

```
radimkocourek94.github.io/
├── .github/workflows/deploy.yml   # build → upload → deploy
├── docs/
│   ├── case-studies/              # grounded portfolio case studies
│   ├── samples/                   # invented-but-realistic docs set ("Taskline")
│   └── meta/                      # this section
├── src/
│   ├── components/                # BeforeAfter, Diff, Metric, Callout
│   ├── css/custom.css             # single accent color, clean default theme
│   └── pages/                     # landing + About
├── sidebars.ts                    # three autogenerated sidebars
└── docusaurus.config.ts
```

## CI/CD pipeline

The workflow in [.github/workflows/deploy.yml](https://github.com/radimkocourek94/radimkocourek94.github.io/blob/main/.github/workflows/deploy.yml):

1. **Build** on every push to `main`: `npm ci`, `npm run build`.
2. **Deploy** the static `build/` output with the official Pages actions.

Two more workflows keep the content honest:

- **Lint** ([lint.yml](https://github.com/radimkocourek94/radimkocourek94.github.io/blob/main/.github/workflows/lint.yml))
  runs Vale on every push and PR — a checked-in style package
  (`styles/Portfolio/`) and a project vocabulary, so the prose is linted
  like the code.
- **Link check** ([link-check.yml](https://github.com/radimkocourek94/radimkocourek94.github.io/blob/main/.github/workflows/link-check.yml))
  runs lychee weekly against `docs/` and `src/pages/` to catch drift
  before a recruiter does.

The whole pipeline runs in about a minute. Reviewing a change means reading
its rendered diff — the rendered page is the artifact under review.

<Callout type="decision">
No blog plugin. The case studies are the content; a rotating blog would
dilute them. If long-form updates are ever needed, adding the plugin is a
one-line change in `docusaurus.config.ts`.
</Callout>

<Callout type="decision">
Cookieless analytics (Betterlytics). A site that argues for signal-driven
documentation should have its own signal. No cookies, no consent banner —
the free tier covers expected traffic.
</Callout>

## Design decisions

- **Clean default theme, one accent color.** The brand is "competent docs",
  not visual novelty.
- **The sidebar mirrors the pitch.** Nav: Case studies, Samples, Meta.
  Every entry either demonstrates writing craft or documents its own
  infrastructure.
- **Custom MDX components** (`BeforeAfter`, `Diff`, `Metric`, `Callout`)
  carry the content-design argument inside the prose.
